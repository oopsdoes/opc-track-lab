# 阶段 5 · MVP 设计

> 蒸馏自 easychen/opc-methodology 官方技能 `opc-mvp-designer`（SKILL.md + experiment-template、mvp-patterns），中文改写版（2026-10）。冲突时以官方为准。

## 目标

确定"**最先验证什么、用什么最小形式去验证**"，而不是替用户定一个产品。

**核心认知（教学模式必讲）**：MVP 不是"简陋产品"，而是"最小验证"。不是功能越多越好，一人公司更要先跑通最小闭环。

## 边界

**不做**：具体内容选题/文案/帖子、完整转化路径、交付 SOP——出现即记录并拉回："这些执行细节会在转化闭环阶段处理。现在先把验证路径的框架确认好。"

## 输入

读 `opc-doc/outputs/04-business-model/risky-assumptions.md`（高风险假设清单）——MVP 的任务就是验证它们。用户想一次验证太多 → 帮助收缩成**单一主验证目标**。

## 常见 MVP 形态（3 选 1 或组合 + "4. 我有自己的方案"）

| 形态 | 是什么 | 适合 |
|------|--------|------|
| 服务型 | 标准化服务包（先用人肉交付验证需求） | 高信任、高定制领域 |
| 内容型 | 低价试用或专题产品（用内容测付费意愿） | 知识、经验类 |
| 工具型 | 最小功能原型 | 明确的工具需求 |
| SaaS 型 | 单场景单结果版本 | 软件/出海工具站 |

**优先选择能最快验证付费意愿的形态。**

⚠️ **MVP 不一定是软件**：线下生意同样适用——一次真实出摊、一单手工接龙、一场收费小课，都是 MVP。验证逻辑完全一样：最小成本 + 最快碰到真金白银的付费反馈。

**出海工具站快速形态**（详见 overseas-loop.md）：AI 编程 + PocketBase/Supabase + Vercel/Cloudflare Pages，3 天上线的单场景工具；发现值得参考的开源同类时给 Zread.ai 链接研究其思路（不是照抄代码）。

## 实验计划五要素（确认 MVP 形态后逐项落实）

1. **要验证的假设**（来自高风险假设清单的第一条）
2. **验证对象是谁**
3. **最小实验是什么**
4. **成功标准是什么**（可判定的数字或事实，如"N 人付费""转化率 ≥X%"）
5. **失败后如何调整**

## MVP 到期验收（Jev 判断关节点）

MVP 跑完到期时，对照上面预先写死的成功标准判"达成/未达成"——**标准早已写死，不许事后移动球门**。判定走判断关：AI 初判 + 判卷模型复判（`scripts/jev-check.py`，考卷材料=experiment-plan.md 的标准+用户提供的执行数据），双列对照呈现，分歧项用户终判。验收记录写入 `opc-doc/outputs/06-mvp-design/verification-[YYYYMMDD].md`。未配置判卷模型时标注「单阅卷」。

## 人机分工

明确 MVP 执行中哪些环节人工做（判断、关系、交付中的信任部分）、哪些交给 AI（生成、整理、自动化）——一人公司的产能天花板取决于这个分工设计。

## 落盘检查点（用户确认后立即执行）

1. `opc-doc/outputs/06-mvp-design/mvp-spec.md` — 验证假设 + 最小验证形式 + MVP 边界
2. `opc-doc/outputs/06-mvp-design/experiment-plan.md` — 五要素 + 验证周期
3. `opc-doc/outputs/06-mvp-design/human-ai-split.md` — 人工 vs AI 分工
4. `opc-doc/state/current-stage.json` → `{"stage":"06-mvp-design","status":"completed","next_stage":"07-conversion-loop","summary":"一句话 MVP 核心"}`；`assumptions.json` 更新已验证/待验证状态
